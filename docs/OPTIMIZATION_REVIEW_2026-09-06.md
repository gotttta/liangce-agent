# 项目优化清单

评审日期：2026-09-06

## 评审范围与结论

本清单基于评审时的当前工作区，包含尚未提交的 V3 改动，覆盖核心工作流、Pipeline DSL、算子、算法库、UI 和测试。它是本次代码评审的独立记录，不替代其他历史方案，也不代表以下优化已经实施。

当前项目适合作为交互式视觉算法开发原型。工程闭环比效果验证更成熟，尚缺独立证据证明其在新图片上的检测准确率、量测可靠性及人工效率收益。

验证记录：

- 使用 `.venv/bin/python -m pytest -q`，164 项测试通过，耗时 19.23 秒。
- 测试产生 735 条警告，主要涉及依赖兼容性和 API 弃用；警告数量不等于缺陷数量。
- 额外复现候选上限失效、算子版本不匹配仍通过校验的问题。
- 五图基准清单引用的 5 个真值文件在当前工作区均不存在。
- 未调用付费模型，未进行新的真实模型端到端评测或 UI 人工体验测试。

### 首轮实施记录

以下各节的“现状”保留评审时证据；实施后的状态以本表和本记录为准。

- 候选预算在规划和执行入口共同生效；同图真值校准有独立的 `max_calibration_candidates` 参数，默认 6，设为 0 可关闭追加校准候选。每轮保存 `candidate_budget.json`。
- 版本不匹配或版本表不完整时拒绝执行；不兼容候选会记录失败，不中断其他候选。归一化保留版本与 Skill 来源。旧的无版本记录允许执行并标明本次补录，自定义算子使用自身版本。
- 每轮新增 `runtime_environment.json`，记录实际 Python、依赖版本与源码哈希，不读取环境变量或密钥。
- 算法库先搜索全部记录再限制返回数量，列表展示仍保留分页上限。
- 进度事件聚合与候选展示迁入 `ui/utils/progress.py`，原导入路径保持兼容；修复 `selected_for_review` 被显示为失败的状态映射。任务恢复、反馈和布局的大范围拆分尚未完成。
- 新增 Python 3.12 声明及运行、开发两份带哈希的依赖锁文件；清理运行路径上的 Pillow 和 scikit-image 弃用调用，保持形态学边界处理与固定基线一致。
- 补充 V3 DAG 对自定义沙箱步骤上限的检查。

验证结果：Python 3.12.14 的独立虚拟环境按带哈希锁文件安装后，181 项测试全部通过（56.33 秒）；固定像素基线通过，CLI 帮助入口正常，Web 在 `http://127.0.0.1:7861` 返回 HTTP 200 并完成浏览器渲染检查。没有调用付费模型。仍有第三方库及测试代码的弃用警告，未通过全局屏蔽方式消除。

关闭校准候选不等于独立评测模式：只要向图传入真值，现有流程仍会按真值排序和复查。独立评测时应完全不向图提供真值，仅在运行结束后评分。

## 01. 建立独立效果评测

### 现状与影响

`data/benchmarks/outline5/manifest.json` 引用的 5 个真值文件均缺失，当前无法直接用该清单完成量化回归。

`tests/test_agent_loop.py::test_ground_truth_calibration_fixes_elliptical_nanohole_sample` 使用同图真值生成调参候选，再用该真值挑选并验证结果。这能验证同图校准功能，但不能证明新图片上的泛化能力。同图校准结果与独立测试成绩需要分别报告。

### 修改方向

- 补齐基准图片对应的真值，或提供明确、可执行的数据获取和生成流程。
- 将调参用图与独立测试图分开；同源图片的相邻裁剪应避免跨集合造成信息泄漏。
- 评测至少覆盖周期背景、低对比度、边框和比例尺干扰，以及适用场景内的无缺陷图片。
- 对比固定 Pipeline、模型规划 Pipeline、启用历史算法复用三种方式。
- 同时记录 Dice、Precision、Recall、边界 F1、数量误差，以及耗时、模型调用成本、人工修改次数和最终验收结果。
- 真实模型评测记录模型配置及运行次数，保留失败样本，避免只展示最好的一次。

### 验收标准

- [ ] 基准清单中的图片和真值都能解析，缺失数据会明确报错。
- [ ] 提供可执行的评测入口，输出逐图结果、汇总结果和失败记录。
- [ ] 独立测试过程不使用测试真值生成候选、调整参数或选择结果；真值仅用于事后评分。
- [ ] 同图交互校准与独立测试采用不同报告口径。
- [ ] 根据实际业务容忍度确定验收阈值，并报告适用范围。

## 02. 落实算子版本回放契约

### 现状与影响

涉及 `core/pipelines/dsl.py` 中的 `normalize_pipeline`、`pin_pipeline_tool_versions`、`validate_pipeline` 和 `execute_pipeline`。

当前记录了 `tool_versions`，但校验和执行未强制匹配历史版本。归一化会丢失版本及 Skill 元数据，重新记录版本时使用当前注册表版本覆盖历史信息。

评审复现：将 `global_threshold` 的记录版本设置为不存在的 `999.0.0`，校验仍通过，重新记录后变成当前版本。未来升级算子实现时，旧算法可能静默产生不同结果。

### 修改方向

- 区分新算法的版本记录与历史算法的版本校验，禁止把历史版本静默替换成当前版本。
- 在归一化、保存、读取和执行的整个链路保留 `tool_versions` 与 Skill 来源信息。
- 优先采用明确拒绝不兼容版本的简单方案；确有需求后再增加多版本实现加载。
- 为无版本的旧记录定义兼容策略，显式标记来源及迁移行为。
- 记录与回放相关的代码修订和依赖环境信息，避免仅靠版本字符串承诺像素级一致。

### 验收标准

- [x] 版本匹配的历史算法可以执行。
- [x] 版本不匹配时明确失败或进入显式迁移流程。
- [x] 保存、读取、归一化后，版本和 Skill 来源信息保持完整。
- [x] 算子升级并更新版本号后，旧算法不会无提示地改用新实现。
- [x] 对固定图片及固定环境验证回放结果一致性。

边界：算子实现修改时仍需要开发者更新版本号。源码哈希能追溯未更新版本号的变更，但当前不会自动按哈希阻止执行。

## 03. 修复候选数量上限

### 现状与影响

`core/agent_loop.py::_fit_candidate_budget` 在 `limit == 1` 时直接返回全部候选。

评审复现：传入 3 个不同候选，设置 `max_candidates=1`，实际返回 3 个。Web 默认使用 1，因此每轮单候选的约束可能失效，增加执行耗时和复查输入量。

此外，`run_planned_agent` 会在读取同图真值后追加校准候选，需要明确这部分是否属于同一个执行预算。

### 修改方向

- 上限为 1 时只保留一个符合当前轮次策略的候选。
- 保留“修订轮优先执行新方案”的语义，避免持续回放旧方案。
- 在执行入口统一约束实际候选数量，覆盖规划、历史回放和真值校准路径。
- 若校准候选使用独立预算，采用单独配置并在记录中明确展示。

### 验收标准

- [x] 候选数超过上限时，预算 1、2、3 均按约定生效。
- [x] 新方案与历史方案共存时，修订轮不会只运行旧方案。
- [x] 实际执行次数符合配置，而不只是规划列表长度符合配置。
- [x] 真值校准不会绕过约定的预算。

## 04. 修复算法库检索范围

### 现状与影响

`core/algorithm_registry.py::search` 调用默认限制为最近 100 条的 `list_algorithms()` 后再计算相似度。较早的算法即使完全匹配，也不会进入候选集。

当前算法数量较少时影响有限，积累超过 100 条后会直接影响经验复用。

### 修改方向

- 将展示列表的分页限制与检索数据范围分开。
- 在全部可用算法中评分后再截断返回结果，或采用能覆盖完整数据的索引。
- 保留人工约束依赖的过滤规则。
- 暂不以引入向量库为前提，先验证现有字段匹配的召回能力。

### 验收标准

- [x] 构造超过 100 条记录，最早的完全匹配算法仍能被检索到。
- [x] 返回数量仍遵守调用方的 `limit`。
- [x] 默认检索仍排除依赖人工空间约束才能回放的记录。

## 05. 拆分 UI 业务职责

### 现状与影响

评审时 `ui/annotation_app.py` 共 2035 行，承担任务恢复、反馈保存、运行调度、流式输出和布局构建等职责。`ui/handlers/` 中部分函数主要转发到该文件，实际职责尚未迁出。

风险在于状态和返回值约定分散，修改交互行为需要同时理解多段业务逻辑。

### 修改方向

- 按任务恢复、反馈处理、Agent 调用与流式事件、结果操作、布局装配逐步拆分。
- 实际迁移实现，避免只增加转发层。
- 将业务结果与 Gradio 组件更新分开，减少跨层传递的位置元组。
- 每次只迁移一个完整职责，控制改动范围。

### 验收标准

- [ ] 业务逻辑有明确归属，布局入口主要负责组件和事件绑定。
- [ ] 新建、恢复、提交、修改、验收、退出流程保持正确。
- [ ] 现有 UI 和适配器测试通过，并对迁移涉及的关键流程做实际交互检查。
- [ ] 不以文件行数下降作为唯一完成标准。

## 06. 固定运行环境与依赖

### 现状与影响

`requirements.txt` 中大部分依赖未锁定，项目没有明确的 Python 支持版本声明。本次测试环境为 Python 3.14，出现 Pydantic V1 兼容性提示，以及 Pillow、scikit-image、Gradio 的 API 弃用提示。

测试通过说明当前环境能完成已有用例，但不足以保证新机器安装和未来升级后的行为一致。

### 修改方向

- 选择并声明经过验证的 Python 版本。
- 提供可复现安装的锁定依赖，区分运行与开发测试依赖。
- 逐项处理实际使用路径上的弃用 API，避免全局屏蔽警告。
- 在 README 补充环境创建、依赖安装、测试和启动步骤。

### 验收标准

- [x] 干净环境按锁文件可完成安装和全部测试（macOS arm64 / Python 3.12.14）。
- [x] CLI 与 Web 入口均可启动。
- [x] 所选 Python 版本未出现此前 Python 3.14 的 Pydantic V1 兼容性提示。
- [x] 依赖升级有明确验证流程，固定基线结果仍符合预期。

## 07. 按需求补充物理量测标定

### 现状与影响

`core/measurement/area.py::measure_components` 当前提供像素面积、数量、包围框等结果，并拒绝未标定的物理单位。拒绝伪装成物理单位是正确行为，但项目尚不能承担物理尺寸量测需求。

### 修改方向

- 先确认目标是辅助标注，还是需要输出纳米、微米等物理量测结果。
- 若需要物理量测，增加像素尺寸、单位和标定来源，必要时分别支持 X/Y 像素间距。
- 同时保留像素值和物理值，明确长度与面积单位。
- 将标定信息随任务与量测产物保存。

### 验收标准

- [ ] 无标定信息时继续拒绝物理单位。
- [ ] 已知尺寸的合成样本可正确换算长度与面积。
- [ ] 面积换算使用 X/Y 像素间距的乘积。
- [ ] 标定信息可追溯，图片裁剪或缩放后的坐标与尺度关系明确。

## 实施顺序与保留原则

建议先修复候选预算和版本回放，同时准备独立评测数据；随后修复检索范围、固定环境，再按迭代需要拆分 UI。物理标定由产品需求决定是否实施。

现有设计中应保留的部分：模型规划与确定性像素执行分离、类型化 DAG、本地校验、人工验收边界、失败记录和可回归基线。

单用户、本地文件存储、Gradio 和人工验收本身不属于本次缺陷。当前没有证据要求立即引入多 Agent、向量数据库或更复杂的服务架构；先验证现有能力是否改善新任务的效果、耗时和人工修改量。
