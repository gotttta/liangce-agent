# 输入到输出全链路审计（2026-09-20）

结论：像素数组进入 LLM 的主要问题已修复，但系统尚未形成贯穿输入、算法、证据和验收的统一契约。最优先的风险是错误的输入关联、被改变的验收依据，以及最终产物之间不一致。不能仅凭已有回归测试通过，认为全链路准确性已有保证。

本轮只审计，不修改业务代码。审计对象是工作区当前版本，包含尚未提交的既有改动和上一轮上下文修复。
先检查统一日志，最后业务记录仍为 2026-09-20 12:22:13，因此该日志只能佐证旧运行，不用于证明新代码在线运行效果。
检查覆盖：上传与反馈、记忆、提示词构造、规划工具、DSL、沙箱数据接口、执行器、评审、自动修订、最终展示、保存与验收。

验证方式：

- 使用临时目录和合成图像做最小复现；部分执行器复现用可信内置算子替代 Docker 调用，隔离检查编排逻辑，没有在宿主运行生成代码。
- 未调用付费模型，未启动真实用户任务；没有把静态或离线复现当作模型准确率实测。

## 已确认问题

### 1. [P1] 更换原图后，旧 Ground Truth 与旧画笔反馈仍可进入新任务

位置：

- ui/annotation_app.py:565：未上传新 GT 时直接返回任务原记录。
- ui/annotation_app.py:1137、1300：使用记录中的旧 GT，不检查其 target_image_path 或内容哈希。
- ui/annotation_app.py:265：从整个任务的 events.jsonl 合并所有历史画笔反馈，仅检查尺寸。
- core/memory/service.py:66：虽然清空 previous_state，却没有清理任务级 GT 和历史反馈来源。

复现：同一任务由 a.png 切到同尺寸 b.png，GT 仍绑定 a.png；给 b.png 添加新画笔标记后，a.png 上的旧排除位置重新出现在反馈 Mask 中。不同尺寸则可能因历史反馈形状不同而报错，清空当前画板也不能删除旧事件。

影响：新图被旧图的答案和人工修正支配，模型或算法会向错误目标优化。

建议：所有像素坐标证据绑定 input_sha256 和坐标变换版本；换图时只加载哈希一致的 GT、画笔和实验。任务语义要求与图片局部约束分别存储。

### 2. [P1] 导入二值 Ground Truth 时会修改真实标注

位置：core/reference_extraction.py:46、64、70、72。

二值 Mask 与彩色轮廓共用闭运算、RETR_EXTERNAL、面积过滤和填充。已经准确的 Mask 也会填洞、连接相邻区域并移除小目标；全空 GT 直接拒绝。

复现：40×40 的环形二值 Mask 原有 500 个前景像素，导入后变成 900 个，孔洞被填满；单像素目标被拒绝。

建议：显式区分二值标签和需要提取的彩色轮廓。二值标签保持逐像素不变，允许无缺陷标签；轮廓推断须有预览、来源和提取参数，不能覆盖原始真值。

### 3. [P1] 自动修订可以重新定义验收目标

位置：core/agent_graph.py:225、373、752、794；providers/vision.py:1273。

初次运行 task_contract 默认为空，初次理解节点未将原始验收条件固定为契约。第一次 revise 时，却从新的模型理解创建契约；rendering 和 target_constraints 也继续使用新理解的值。

复现：最初条件“所有目标都闭合，荧光绿”，修订模型返回“只标中央目标、红色”，下一轮验收目标变为“只标中央目标”。任务文字仍可能保留，但结构化验收依据已经漂移。

另外，normalize_acceptance_criteria 只返回四个字段，count_policy、expected_count、count_source 在图节点及评审再次规范化时被丢弃。

建议：首次形成带来源、版本的任务契约；仅用户明确变更能更新。算法修订只改方案，不改要求。契约应包含数量策略、单位、输出类型、显示要求与验收条件，规范化保持幂等。

### 4. [P1] 尺寸数字被误识别为必须匹配的目标数量

位置：providers/vision.py:1124；core/quality.py:70。

数量提取正则允许数字后没有计数单位，并允许“检测”等动词后跟其他文字。

复现：“检测直径10像素的孔”得到 expected_count=10；“检测面积100像素以上的缺陷”得到 100。它们随后会以 user_explicit 的身份参与硬数量门禁。

建议：数量、长度、面积等分别解析，必须有明确计数语义才建立硬数量条件；不确定时不从数字猜数量。增加否定、上限、范围、尺寸混合表达的测试。

### 5. [P1] Ground Truth 分支把像素重叠达标等同于整项任务通过

位置：core/agent_graph.py:546、617、648；core/measurement/evaluation.py:6。

有 GT 时完全绕开视觉/任务条件评审，只检查四个重叠/边界指标，不检查目标分离、数量、颜色、输出类型和专用量测是否交付。

复现：两个 10×10 方块用两个像素的细桥连为一个目标，Dice=0.995025、recall=1、precision=0.990099、boundary_f1=1；实际数量 1、GT 数量 2，但判断为 present。

建议：把“像素指标达标”“任务条件达标”“显示/交付符合要求”分别判定；任务整体通过必须满足所有适用条件。GT 替代重叠判断，不替代整个验收契约。

### 6. [P1] 人工修正后，最终 Mask、导出轮廓和结构化测量不是同一版本

位置：core/experiments/runner.py:83、120、140、159。

先导出 outputs 与轮廓，然后修改 execution.mask，再重算通用连通域测量。最终 contours.json 仍来自修改前的 execution.contours；measurements.structured_outputs 也包含修改前的结果。

复现：用排除画笔删除唯一的 100 像素目标，mask.png 已为空、通用 measurement count=0，但 outputs.json 仍有 100 个前景像素，contours.json 仍含 1 条轮廓。

保留原始数据本身合理；问题在于原始数据与最终数据共用未明确分阶段的交付名称。上一轮模型摘要已注明 raw stage，但用户下载文件及最终轮廓仍不一致。

建议：raw、constrained、final 三阶段显式区分；所有最终轮廓和依赖 Mask 的测量基于最终 Mask 重算，无法重算的专用测量明确失效。最终交付 manifest 指向同一版本的产物。

### 7. [P1] 显式声明的图片/结构化输出会被中间 Mask 抢占

位置：core/pipelines/dsl.py:657；core/experiments/runner.py:87。

即使 outputs 只声明 final_image 或 measurements，DSL 仍回退选择最后一个内部 Mask。执行器只看 execution.mask 是否存在，因而进入分割渲染分支。

复现：节点包含 internal_mask 与 final_image，outputs 仅声明 result_image；execution.mask 仍非空。自定义最终图可能被忽略，显示的是内部 Mask 的默认叠加。

建议：outputs 显式存在时以它为唯一出口；只对未声明出口的旧流水线推断最终 Mask。根据输出契约分发渲染，而不是扫描是否曾生成 Mask。

### 8. [P1] “执行健康检查”提前否定合理的零缺陷和大目标结果

位置：core/quality.py:40、60、79；core/experiments/runner.py:163；core/agent_graph.py:531。

默认 coverage>35% 或空 Mask 均不可评审。视觉模型根本看不到这些候选，却会触发自动换算法。

复现：无缺陷空 Mask 被标记 no_annotation；覆盖 49% 的单一目标被 coverage_too_large、dominant_component 拒绝。

建议：执行健康只拒绝格式损坏、非有限值、错误尺寸等；空结果、大面积、接边等默认是诊断线索。是否允许零缺陷、目标覆盖范围应来自任务要求，不能由通用缺陷先验决定。

### 9. [P2] 图像入口缺乏统一格式与位深契约

位置：providers/vision.py:1365；core/preprocessing.py:12；ui/annotation_app.py:2080。

上传允许一般 image 文件，模型入口却将所有非 JPEG 文件声明成 image/png 而不转码。算法入口统一 convert("L")，丢失高位深数据。

复现：TIFF 文件原字节被声明为 PNG；16位像素 [0,256,1024,65535] 进入算法后变为 [0,255,255,255]。

建议：原始科学图像保留位深；算法输入和视觉预览分别生成，记录强度映射、方向和坐标变换。图片请求使用实际支持的格式和正确 MIME；不支持的类型在入口明确拒绝。

### 10. [P2] 最终渲染会改变图片输出的颜色和亮度

位置：core/experiments/runner.py:94。

任何 ImageArtifact 都先按全图 min/max 拉伸到 0–255，无法区分已经完成的 RGB 标注图与需要归一化的数值响应图。常量图直接变黑；结构化 boxes/points 还硬编码红色。

复现：算法输出全图 RGB=(128,128,128)，实际 result_annotation.png 为 (0,0,0)。

建议：ImageArtifact 明确颜色空间、数值范围和用途。最终 RGB 图保持像素；中间强度图才应用明确的显示映射。结构化标注统一使用任务 rendering。

### 11. [P2] 接触图像边缘的 Mask 没有完整绘制边界

位置：core/visualization.py:84。

边界仅比较图像内部相邻像素，没有把图外当背景。全前景 Mask 不会画任何轮廓；接边目标缺少沿图像边界的线段。

复现：5×5 全前景 Mask，_mask_boundary 返回 0 个边界像素。

建议：定义裁切目标的显示规则，使用补背景后的边界提取或显式补四边；区分真实可见边界与图像截断边界。不要让模型反复修改正确 Mask 去补偿渲染缺陷。

### 12. [P2] 评审切换候选后，聊天中的数量仍可能来自旧候选

位置：core/agent_loop.py:218、527；ui/gradio_adapters.py:4。

conversation 在临时选择首个候选时构造；promote_candidate_result 更新测量、图片与流水线，却不更新 conversation。

复现：从 1 个目标的候选切到 5 个目标的候选后，measurements count=5，聊天仍说“本轮标出1个区域”。

建议：所有面向用户的结果文字从最终选定状态生成，不把临时结论作为静态聊天文本传递。候选切换也应清理新候选不存在的旧文件。

### 13. [P2] 事件监听器既不按请求隔离，也没有异常清理保证

位置：core/agent_events.py:11、41；ui/annotation_app.py:1113、1388。

事件广播给进程内所有监听器。UI 只在成功返回时注销；输入异常、模型异常和查看产物的提前返回都会遗留监听器。

复现：一次缺少图片的请求之后监听器从 0 增至 1；注册两个请求监听器后，A 的事件会同时被 B 接收。并发时进度、模型内容及 token 统计可能串任务；异常后遗留队列持续积累事件。

建议：事件携带 task/run ID，按请求订阅；注册/注销用 try/finally 或上下文管理器。流式工作线程还需要取消与总时限，而不仅依赖单次 SDK 超时。

### 14. [P2] 长流水线源码在修订上下文中仍被字符截断

位置：providers/vision.py:710。

summarize_pipeline_for_context 保留源码，但随后 _compact_json(...,16000) 对整个序列化结果切片。标记可见，但 JSON 与源码不完整；提示词同时要求原样复用完整生成算子。

复现：22,042 字符的合法算子源码进入修订提示后被截断，无法作为完整可编辑基线恢复。

建议：使用版本化算子 ID 和哈希；提供精确源码读取或按节点补丁协议。不要把不完整源码伪装成可直接复用的完整 Pipeline。

## 其他设计限制：需优化，但不等同于已证明在线准确率下降

1. **新摘要策略仍是“前几项”**：core/experiments/context.py:35 的表格样本有明确 partial 标记，但没有异常、极值、分布摘要。恰好在尾部的坏样本不主动显现。应按业务指标生成统计与异常索引，不以样本顺序代替重要性。
2. **按需取证预算不匹配分页深度**：所有检查共享 3 次预算（core/tools/budget.py:9），每页最多20项，查目录/深入selector/看局部图也消耗预算。对复杂任务可能不足；应区分导航与有效取证，并根据未解决验收条件调整预算。
3. **文本超限只有失败出口**：core/model_context.py:50 防止巨量输入有效，但尚无自动卸载可恢复历史、重试或降级路径。图像只统计数量和编码长度，不限制视觉开销。历史工具图片和参数还会继续附带在消息历史里。
4. **提示词仍全量注入自定义算子源码**：providers/vision.py:904 遍历整个可复用算子库；库增长后，无关代码也会进入每次理解请求。应索引检索后按需读取。
5. **摘要调用绕过统一统计和预算**：providers/vision.py:314 的非流式 conversation summary 直接调用 SDK；该部分耗时和 usage 不进入主调用统计。单条超长历史消息也可超出 conversation 的批次目标。
6. **试验与正式执行的条件不同**：core/tools/experiments.py:154 未向 runner 传 rendering、target_constraints、ground_truth_mask；正式工作流会传。试验看到的颜色、健康判断与正式执行可能不同。应共享可追溯的 ExecutionSpec。
7. **上下文缩小了，内存/磁盘仍大量重复数组**：quality.outputs、measurements.structured_outputs、候选记录、graph state、trajectory 和记忆重复嵌套完整数据。旧运行 iteration_1 的 graph_state.json 约26MB、candidate_summary.json约17MB。应让大型状态只持有产物引用；避免把完整质量报告写入每条记忆。
8. **沙箱传输仍为展开的 JSON 数组**：core/sandbox.py:126 在 float32 输入超过8MiB时拒绝（约210万灰度像素）；2048×2048 灰度图会超限。小图可运行，但工业大图需要二进制数组协议、分块和独立资源预算。

## 修复建议顺序

1. 输入和任务真值：图片哈希隔离、GT 保真、数量语义、不可漂移的任务契约（1–4）。
2. 执行和交付一致性：显式输出契约、最终 Mask 派生产物一致、零缺陷合法结果（6–8）。
3. 评审正确性：像素指标与任务验收组合，不以重叠率替代完整验收（5）。
4. 图片和交互：位深/MIME、渲染、最终文本、事件隔离（9–13）。
5. 运行成本：完整源码按需读取、按证据需要分配预算、产物引用化和二进制传输（14及设计限制）。

建议新增固定回归集：换图但同尺寸、环形GT、零缺陷、小于4像素目标、相邻目标粘连、接边目标、高覆盖目标、16位TIFF、显式图像出口含中间Mask、人工排除后导出、评审换候选、模型失败后重试及并发两任务。每类先做确定性测试，再做真实模型验收对照。
